# Communications Strategy

## Purpose

Present Ferris from demonstrated owner outcomes and exact authority boundaries.
Product summaries must point to
[`Ferris Current Strategy and Feature Set`](../plans/FERRIS_CURRENT_STRATEGY_AND_FEATURES.md);
specifications and retained evidence remain authoritative for contract details.

## Lead message

> Ferris is an owner-first build, validation, execution, and evidence layer for
> Rust repositories and applications. It makes existing work selectable,
> explainable, bounded, and auditable while Cargo and repository owners retain
> command, policy, success, and publication authority.

The governing phrase is:

> **The plan is global; the work is local.**

## Audience and proof

| Audience | Lead message | Required evidence | Do not claim |
|---|---|---|---|
| Contributor | Ferris can explain selected owner work and run an explicitly approved Action Plan. | Exact source, plan, owner command, result, and receipt identities. | One command understands every repository automatically. |
| Repository owner | Owner declarations and commands stay authoritative, unknowns widen, and adoption is removable. | Selection controls, fallback controls, direct-owner comparison, and removal drill. | Ferris replaces repository policy or required CI. |
| CI/platform owner | Revision binding, replay, scheduling analysis, and artifact qualification provide portable evidence around existing provider workflows. | Exact tested revision, provider context, bounds, and owner-owned execution result. | Revision evidence is execution attestation or replay is live scheduling. |
| Reviewer/security | Execution is approval-bound, inputs and output are bounded, and receipts fail closed. | Negative controls, mutation tests, cleanup evidence, and authority review. | Integrity proves provider authenticity or release approval. |
| Engineering lead | PARLOR, RUNE, ICELINES, and BISECT demonstrate complementary owner-first boundaries. | Named adopter, revision/run, scenario, result, and limitation. | Realized savings, CI equivalence, or production readiness. |

## Pull request story

1. **Problem:** Cargo and repository-native tools correctly own local work, but
   repositories lack one deterministic layer for cross-scope planning,
   conservative validation selection, approved execution, and portable evidence.
2. **Strategy:** keep all native authorities in place and add bounded,
   owner-declared contracts around them.
3. **Current capability:** workspace and federated planning, owner-domain and
   revision-bound validation, Action Plan execution and receipt verification,
   replay, scheduling analysis, and artifact qualification.
4. **Proof:** PARLOR covers owner-native execution and removal; RUNE covers a
   distinct Cargo topology; ICELINES covers cross-platform artifacts; BISECT
   covers polyglot domains and large revision-bound plans.
5. **Boundary:** no workflow parsing, command inference, checkout mutation,
   remote execution, live scheduling, artifact transport, required-gate
   deletion, savings claim, or CI-equivalence claim.
6. **Review ask:** evaluate whether the bounded contracts, tests, adopter
   evidence, and non-goals justify continuing the incubation.

## Evidence language

| Evidence level | Allowed language |
|---|---|
| Implemented | Name the exact command, schema, bounded behavior, and passing tests. |
| Local proof | Name repository, revision, platform, owner comparison, and limitations. |
| Hosted shadow | Name workflow run and tested revision; state that existing workflows remain authoritative. |
| Cross-platform match | Name the compared identities and environmental differences. |
| Projection or replay | Say "projected" or "replayed"; never convert it to realized savings. |
| Production outcome | Use only after separately approved deployment, denominator, observation window, and owner acceptance. |

## Release and adoption rules

- Lead with current capabilities and owner outcomes, not implementation
  chronology or unproven time-saving targets.
- Identify every number as measured, replayed, projected, or hypothetical.
- Report negative controls, fallback, unsupported surfaces, and narrowed scope
  with the same prominence as successful proof.
- Keep implementation, adopter evidence, support status, and merge readiness
  distinct.
- Preserve historical documents as point-in-time evidence; update front-door
  summaries rather than rewriting their chronology.
