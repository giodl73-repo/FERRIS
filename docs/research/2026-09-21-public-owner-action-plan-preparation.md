# Public Owner Action Plan Preparation Evaluation

Date: 2026-09-21

Status: completed bounded adopter evaluation

## Question

Can the current Ferris preparer consume an entrypoint declaration generated by
a public repository-owned integration, rather than an evaluator-authored
synthetic declaration, without launching owner work or retaining consumer
changes?

## Controls

- Consumer: `giodl73-repo/PARLOR` worktree at
  `ff856a6940ccdb05f8f028c3b07a461c3a34f9f3`.
- Owner source: committed `tools/ferris-go/run.py`, introduced by the PARLOR
  owner and documented as PARLOR-owned command and topology policy.
- Mode: the owner adapter's `--full --prepare-only` path followed by one Ferris
  `quality-fmt` lane preparation.
- No approval was created for the prepared Ferris plan, no owner command was
  launched, and no tracked consumer file could change.
- Completion: repeatable preparation, exact command preservation, unsigned
  rejection, no receipt, and complete removal of generated `.ferris/` state.

## Owner Input

PARLOR's committed adapter generated an existing
`ferris.owner-entrypoints/v1` declaration with:

- declaration ID
  `sha256:d590d7c7ad333d3ce69680648428da4cdb7ca82ac8e5fcb59b2a5815ecb675bc`;
- ten owner lanes;
- 43 bound files;
- repository-local staged Cargo; and
- explicit quality, build, test-build, and package-test commands.

The adapter is a real owner-maintained integration, not a declaration authored
for this evaluation. It remains a non-required shadow and preserves PARLOR's
direct Cargo validation.

## Result

Ferris selected `quality-fmt` and preserved the exact owner command:

```console
.ferris/bin/cargo.exe fmt --all -- --check
```

Two preparations succeeded and were byte-identical.

- Action Plan ID:
  `sha256:98d9d8cec77a67867ff73b713b2e9ccd633f244fe4a609ce2c5e7dbd0d83e9b6`
- Output SHA-256:
  `c778be16bcc1d327e5d6c0c4ec6730dcb21404507b3c1ff55a92593b9be3e95b`
- Prepared lanes: one
- Approval ID: empty

`ferris go` rejected the unsigned plan with exit 2 and
`FERRIS-EXECUTION-IDENTITY-INVALID`. Standard output was empty, the diagnostic
was emitted on standard error, no receipt was created, and no owner process was
launched.

The generated `.ferris/` tree was removed. The PARLOR worktree remained clean
at its original revision.

## Product Finding

This closes the earlier evaluator-authored-entrypoint limitation for the
single-lane preparer. Ferris can validate and compile one entrypoint from an
owner-maintained public integration.

It does not close onboarding:

- PARLOR has no `ferris.environment-requirements/v1` declaration, so there is
  still no owner-maintained readiness and entrypoint pair;
- PARLOR explicitly resolves and copies Cargo into `.ferris/bin`;
- the owner adapter still constructs its ten-lane dependency graph, hashes
  command files, creates approval data, and writes complete execution records;
  and
- the single-lane preparer cannot preserve the owner topology.

The next bounded product candidate is explicit multi-lane plan compilation from
owner-authored entrypoints and lane policy. It must not infer commands,
dependencies, requiredness, limits, or approval. PATH executable support
remains a separately versioned execution problem.

## Reproduction

```console
python tools/ferris-go/run.py \
  --ferris <CURRENT_FERRIS_BINARY> \
  --cargo <EXACT_CARGO_BINARY> \
  --full \
  --prepare-only
```

The two `prepare-action-plan` calls selected `quality-fmt` with PARLOR's exact
gate, topology, timeout, and output bounds. Generated files were removed after
identity comparison and unsigned execution rejection.
